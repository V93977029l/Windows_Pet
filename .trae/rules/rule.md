本报告旨在为准备商业化的Godot游戏项目提供一个全面、可扩展、低耦合的模块化架构方案。该方案专为8人左右的开发团队（或多个职能部门、乃至人与AI Coding Agent混合的团队）设计，以解决多人协作开发中常见的“牵一发而动全身”的痛点。报告将深入探讨Godot模块化设计的核心原则，提供一套具体的、符合工程标准的文件夹结构，并配套一套基于Git和持续集成的成熟工作流。最后，本报告将展望未来，提出一套面向AI Coding Agent的自动化工作流，并提供具体的指令集（提示词），以便让AI助手能够理解并搭建这套架构。

### **引言：商业化游戏开发中的“耦合之痛”**

随着游戏项目规模的扩大和团队成员的增加，软件架构的复杂性呈指数级增长。在一个紧密耦合（Tightly Coupled）的系统中，一个微小的改动可能会像多米诺骨牌一样，引发一系列意想不到的连锁反应，导致大量的回归测试、频繁的合并冲突和不断下降的开发效率。对于一个准备商业化的游戏项目而言，这种“牵一发而动周身”的状态是致命的。它不仅拖慢了开发进度，也极大地增加了维护成本和技术债，使得项目难以适应市场变化和玩家需求的快速迭代。

**核心挑战分析：**

1.  **高耦合度：** 当项目的不同部分（如玩家、UI、战斗系统）之间存在过多的直接依赖时，修改任何一部分都变得极其困难和危险。例如，UI代码直接引用玩家场景树中的某个具体节点，一旦玩家场景结构调整，UI代码就会崩溃。
2.  **多人协作瓶颈：** 在一个8人或更多成员的团队中，如果项目结构不清晰，职责划分不明确，开发者们将不可避免地频繁修改同一批文件，尤其是Godot中的场景文件（`.tscn`）。这会导致大量的版本控制合并冲突，将宝贵的开发时间浪费在解决冲突而非创造价值上 [[1]][[2]][[3]]。
3.  **可扩展性与可维护性差：** 一个单体式（Monolithic）的项目结构，使得添加新功能或替换旧系统变得异常痛苦。新功能的代码需要小心翼翼地嵌入到现有复杂的逻辑中，而旧代码因为盘根错节的依赖关系而不敢轻易移除。
4.  **迎接AI协作时代：** 未来的游戏开发很可能是人与AI Coding Agent协同工作的模式。如果项目架构混乱、模块边界模糊，AI Agent将难以理解代码库的上下文，无法安全、高效地生成或重构代码，甚至可能在无意中破坏项目结构。

**本报告的目标**，正是为了解决上述挑战，提供一个从架构设计理念、具体文件结构，到团队协作流程，再到AI自动化工作流的端到端解决方案。我们将基于Godot引擎的设计哲学，构建一个既符合人类开发者直觉，又能被AI Agent清晰理解和操作的健壮开发范式。

### **第一部分：Godot模块化架构设计的核心原则**

在设计具体的文件夹结构之前，我们必须首先理解并认同支撑这套架构的底层设计原则。这些原则源于Godot引擎自身的特性以及通用的软件工程最佳实践。

#### **1.1 理解Godot的哲学：拥抱场景树与节点系统**

与其他游戏引擎不同，Godot的设计哲学并不强制开发者遵循经典的软件设计模式，如MVC（模型-视图-控制器）。相反，Godot鼓励开发者“自然地思考游戏” [[4]]。其核心是**场景（Scene）和节点（Node）**系统。

*   **场景即组件（Scenes as a Complement）：** 在Godot中，几乎万物皆可为场景。一个玩家、一颗子弹、一个UI按钮，都可以是一个独立的场景。更重要的是，场景可以实例化并作为子节点添加到其他场景中，形成一个场景树 [[5]][[6]][[7]]。这种设计天然地鼓励了“组合优于继承”的原则。我们不应该将一个大型关卡制作成一个包含数千个节点的巨型场景，而应该将其分解为由“玩家”场景、“敌人”场景、“宝箱”场景等多个独立场景组合而成的复合场景。这种组合式的思维是模块化的基石。
*   **节点树的内在组织性：** 节点和场景树的父子关系，本身就提供了一种组织和封装游戏对象行为的方式 [[8]][[9]]。一个`Player`节点（根）可以拥有`Sprite2D`、`CollisionShape2D`、`Camera2D`等子节点，这些子节点共同构成了“玩家”这个完整的概念。
*   **信号：天生的解耦利器：** Godot内置的**信号（Signals）**机制是其设计的精髓之一。它本质上是观察者模式的一种实现 [[10]]。一个节点可以定义并“发出”（emit）一个信号，而其他任何节点都可以“连接”（connect）到这个信号，并在信号发出时执行相应的回调函数。整个过程中，信号的发出者完全不需要知道谁在监听它，从而实现了完美的解耦 [[11]][[12]][[13]]。这是我们实现模块间通信、避免直接引用的首选工具。

#### **1.2 耦合的根源与解耦的核心策略**

耦合度描述了模块之间相互依赖的程度。**紧耦合（Tight Coupling）**意味着模块间关系紧密，修改其一很可能影响其他；**松耦合（Loose Coupling）**则表示模块相对独立，可以被独立地开发、测试和替换 [[14]]。

**在Godot项目中，常见的耦合来源包括：**

*   **硬编码的节点路径 (`get_node("path/to/node")`)：** 这是最常见也是最脆弱的耦合形式。一旦场景树结构发生变化，代码就会立即失效。
*   **跨模块的类直接引用：** 模块A的脚本直接实例化或调用模块B的脚本中的具体方法。
*   **全局单例（Autoloads）的滥用：** 虽然单例很方便，但如果被用作存储全局状态和进行跨模块调用的“大泥球”，它们就会成为项目耦合的中心枢纽。
*   **巨大的、无所不包的场景文件：** 当多个开发者（例如，关卡设计师、程序员、特效师）需要同时修改同一个巨大的关卡场景文件时，版本控制冲突将成为家常便饭。

**我们的核心解耦策略必须围绕以下几点展开：**

1.  **优先使用信号：** 模块间的通信应尽可能通过信号进行。例如，当玩家生命值变化时，`Player`模块不应该直接调用`UI`模块的`update_health_bar`方法，而应该发出一个`health_changed(new_health)`信号。`UI`模块自行决定监听此信号并更新显示。
2.  **定义清晰的模块接口（Interface）：** 每个模块应该只暴露一小组精心设计的公共方法和信号，作为其与外部世界交互的“契约”。模块内部的实现细节应该被隐藏起来。这遵循了软件工程中的**接口隔离原则（Interface Segregation Principle）** [[15]]。
3.  **依赖倒置：** 高层模块（如游戏逻辑）不应直接依赖于底层模块（如UI、音频播放器）。两者都应该依赖于一个抽象的接口或事件总线。例如，游戏逻辑模块发出一个`play_sound("explosion")`事件，而不是直接调用`AudioManager.play_explosion_sound()`。
4.  **物理隔离：** 将每个模块相关的所有文件（场景、脚本、资源）都放在同一个文件夹内。这种物理上的内聚性，是实现逻辑上低耦合的第一步。

#### **1.3 文件夹结构的组织哲学：按功能而非类型**

许多开发者，特别是从Unity等引擎转型而来的，习惯于按资源类型组织文件夹，例如：

```
/scenes
/scripts
/materials
/textures
/audio
```


这种结构在项目初期看似整洁，但随着项目规模的扩大，其弊端会愈发明显。当你想找到与“玩家”相关的所有东西时，你需要在`scenes`、`scripts`、`textures`等多个文件夹之间来回跳转，这极大地增加了认知负荷，并且丢失了文件之间的上下文关联 [[16]][[17]]。这种组织方式本质上是反模块化的。

我们必须采用**按功能（By Feature）**或**按上下文（By Context）**的组织方式。这意味着，与同一游戏功能（如玩家、敌人、库存系统）相关的所有文件都应该被放在同一个专属文件夹中 [[18]][[19]][[20]]。

**按功能组织的好处是显而易见的：**

*   **高内聚性：** 相关的文件物理上聚集在一起，便于查找和理解。
*   **模块独立性：** 每个功能文件夹都可以被视为一个独立的“微型项目”。理论上，你可以将整个`/player`文件夹复制到另一个项目中，稍作调整即可复用。
*   **降低协作冲突：** 如果美术师在修改玩家的贴图，程序员在修改玩家的控制逻辑，他们都只在`/player`文件夹内工作，减少了与其他模块开发人员的交叉影响。
*   **清晰的职责划分：** 可以将整个功能文件夹的所有权分配给某个开发者或小组，权责明确。

### **第二部分：商业级Godot项目的模块化文件夹结构方案**

基于上述原则，我们设计了一套专为商业级项目和多人协作优化的模块化文件夹结构。这套结构旨在实现清晰的模块划分、强制的边界以及高度的可维护性。

#### **2.1 顶层目录结构设计**

这是项目资源路径`res://`（本项目根目录下的transparent-pet文件夹才是Godot的根目录，其他文件夹都是母项目的其他模块，比如GDExtension插件代码）的根目录结构。每个文件夹都有其明确的用途。

```
/ (res://)

|

├── core/                  # 核心系统与基础设施 (Core Systems & Infrastructure)

|

├── modules/               # 游戏功能模块 (Gameplay Feature Modules)

|

├── assets/                # 全局共享资源 (Global Shared Assets)

|

├── addons/                # 第三方插件 (Third-party Addons)

|

├── prototypes/            # 原型与实验区 (Prototypes & Sandbox)

|

├── tools/                 # 自定义编辑器工具 (Custom Editor Tools)

|

├── tests/                 # 自动化测试脚本 (Automated Tests)

|

└── docs/                  # 项目文档 (Project Documentation)

```


**各顶层目录职责说明：**

*   **`core/`**: 存放项目的根基，是所有其他模块依赖的基础设施。这里的代码应具备高度的稳定性和通用性，修改前需要经过严格的评审。可以将其视为游戏的“操作系统” (inspired by [[21]][[22]]。
*   **`modules/`**: 项目的心脏。所有独立的游戏玩法功能，如玩家系统、战斗系统、任务系统等，都以子文件夹的形式存放在这里。这是开发活动最频繁的区域。
*   **`assets/`**: 存放那些被多个模块共享的、不属于任何特定模块的通用资源。例如，通用的UI图标、全局着色器、项目主字体等。
*   **`addons/`**: 用于存放从Godot Asset Library或第三方获取的插件和工具。保持这个文件夹的独立性便于管理和更新外部依赖 [[23]][[24]]。
*   **`prototypes/`**: 一个“沙盒”区域，供开发者进行快速原型设计和功能实验，而不会污染主项目结构。这里的文件不应被正式的游戏逻辑所依赖 [[25]]。
*   **`tools/`**: 存放为提升开发效率而编写的自定义编辑器脚本和工具（`@tool` 脚本）。
*   **`tests/`**: 存放所有自动化测试脚本。一个良好的实践是，其内部结构镜像`core/`和`modules/`的结构，便于定位测试对象。
*   **`docs/`**: 存放项目的设计文档、技术文档、美术规范等。

#### **2.2 核心模块 (`core/`) 详解**

`core/` 模块的目标是提供稳定、可靠的底层服务，并让上层的游戏功能模块与之解耦。

```
core/

|

├── autoload/              # 全局单例/服务

|   ├── event_bus.gd       # 全局事件总线
|   ├── scene_manager.tscn # 场景加载与过渡管理器
|   ├── save_manager.gd    # 存档/读档服务
|   └── config_manager.gd    # 游戏配置管理
|

├── ui_framework/          # UI基础设施

|   ├── base_screen.gd     # 所有UI界面的基类
|   ├── components/        # 通用UI组件 (如自定义按钮, 弹窗)
|   └── theme/             # 全局UI主题 (theme.tres)
|

├── services/              # 抽象服务接口与实现

|   ├── analytics/         # 数据分析服务
|   ├── iap/               # 内购服务
|   └── audio_manager.gd   # 音频管理器 (通常也是单例)
|

└── utils/                 # 通用工具类
    ├── math_utils.gd      # 数学帮助函数
    └── node_utils.gd      # 节点操作帮助函数
```


**关键设计点：**

*   **`event_bus.gd`**: 这是一个至关重要的单例，它实现了发布-订阅模式。模块之间不直接通信，而是向`EventBus`发布事件（例如 `EventBus.publish("player_died")`），或者订阅`EventBus`上的事件（`EventBus.subscribe("player_died", on_player_died)`）。这极大地降低了模块间的耦合。
*   **服务抽象化**: 对于像内购、分析这类服务，`core/` 中应定义其接口，具体的实现可以根据平台（Steam, Mobile）不同而替换，上层模块只与接口交互。

#### **2.3 游戏功能模块 (`modules/`) 设计**

这是体现模块化思想的核心。每个子文件夹都是一个垂直切片，包含了一个完整功能所需的一切。

**以 `player` 模块（虽然当前项目是个桌宠项目，没有Player角色）为例：**

```
modules/

|

└── player/

    |

    ├── scenes/                    # 模块相关的场景

    |   ├── player.tscn            # 玩家主场景 (根节点)
    |   └── components/            # 玩家的组件化场景
    |       ├── health_component.tscn
    |       └── movement_component.tscn
    |

    ├── scripts/                   # 模块相关的脚本

    |   ├── player_controller.gd   # 玩家主逻辑
    |   ├── health_component.gd
    |   └── movement_component.gd
    |

    ├── assets/                    # 模块专属的资源

    |   ├── models/                # 3D模型
    |   ├── textures/              # 贴图
    |   ├── animations/            # 动画 (player.anim)
    |   └── sfx/                   # 音效
    |

    ├── ui/                        # 模块专属的UI

    |   ├── player_hud.tscn        # 玩家的平视显示器 (如血条)
    |   └── player_hud.gd
    |

    └── api.gd                     # 模块的公共接口契约 (关键！)
```


**关键设计点：**

*   **自包含性**: `player/` 文件夹包含了实现玩家功能所需的一切。如果想在另一个游戏中复用这个玩家，理论上只需拷贝整个文件夹。
*   **组件化场景**: `player.tscn` 场景本身可能很简单，其核心功能由多个子场景（如`health_component.tscn`）组合而成。这种细粒度的场景划分，极大地降低了多人编辑同一个场景文件导致冲突的概率 [[26]][[27]][[28]]。
*   **`api.gd` - 模块接口契约**: 这是一个可选但强烈推荐的实践。它是一个脚本（通常附加在模块的根场景节点上，或者作为一个静态类），明确定义了该模块对外暴露的公共接口。
    *   **公共方法**: 如 `take_damage(amount)`。
    *   **公共信号**: 如 `signal health_changed(current_health, max_health)`。
    *   **公共属性**: 如 `var is_invincible: bool`。
    所有其他模块与`player`模块的交互，**必须且只能**通过`api.gd`中定义的接口进行。这为模块间建立了一道清晰的防火墙，也为未来的AI Agent代码生成提供了可解析的契约。

**预创建的其他游戏必要模块文件夹：**

根据商业游戏项目的常见需求，我们预先创建以下模块文件夹结构，团队可以根据实际项目需求进行增删：

```
modules/

|

├── player/                 # 玩家角色、控制、状态等
├── inventory/              # 背包系统、物品管理
├── combat/                 # 战斗系统 (技能、伤害计算、效果)
├── dialogue/               # 对话系统
├── quest/                  # 任务系统
├── world_map/              # 世界地图、导航
├── enemy_ai/               # 敌人AI (巡逻、追击、攻击)
├── level_management/       # 关卡管理、场景加载
├── crafting/               # 制造/合成系统
└── shop/                   # 商店/交易系统
```


#### **2.4 命名规范与项目配置**

*   **命名规范**:
    *   **文件和文件夹**: 使用 `snake_case` (小写字母和下划线)，例如 `player_controller.gd`, `world_map/`。
    *   **节点名称和类名**: 使用 `PascalCase` (驼峰式)，例如 `PlayerController`, `WorldMap`。
    *   遵循这些规范有助于保持项目一致性，并减少因命名不一致导致的混乱 [[29]][[30]][[31]]。
*   **项目配置文件 (`project.godot`)**:
    *   这是一个高冲突风险区，因为它包含了所有人的输入映射、单例加载、渲染设置等。
    *   **标准化策略**: 团队应共同制定一个`project.godot`的管理策略。例如，指定一名技术负责人（或一个小组）专门负责对`project.godot`的修改进行审核和合并。
    *   **解耦配置**: 尽可能将配置信息从`project.godot`中移出，放到自定义的资源文件（`.tres`）或配置文件（如`.json`, `.cfg`）中，这些文件可以存放在各自的模块内。例如，每个模块的输入动作可以定义在自己的配置文件中，由一个核心的`InputManager`在启动时加载。

### **第三部分：支持多人/多Agent协作的成熟工作流**

拥有了清晰的架构，我们还需要一套成熟的工作流来确保团队能够在这套架构上高效、顺畅地协作。

#### **3.1 版本控制：基于Git的特性分支工作流**

Git是现代软件开发的标准，其强大的分支功能是团队协作的基石 [[32]][[33]][[34]]。对于8人规模的游戏团队，我们推荐一种简化版的GitFlow，即**特性分支工作流（Feature Branch Workflow）** [[35]][[36]]。

*   **核心分支**:
    *   `main`: 主分支，永远代表着可发布、经过完整测试的稳定版本。只接受来自`develop`分支的合并。
    *   `develop`: 开发主分支。所有已完成并测试的功能分支将合并到这里。它是下一个发布版本的“集结地”。
*   **支持分支**:
    *   `feature/<module_name>/<feature_description>`: 这是所有开发工作的起点。每个新功能或任务都必须创建一个新的特性分支。例如: `feature/inventory/add_sorting_function`。
        *   这种命名约定将分支与模块直接关联，一目了然。
        *   开发者在自己的特性分支上可以自由地提交和实验，不会影响到任何人。
        *   开发完成后，通过**合并请求（Merge Request / Pull Request）**提交到`develop`分支。
    *   `hotfix/<issue_id>`: 当线上版本（`main`分支）出现紧急bug时，从`main`分支创建热修复分支。修复后，需要同时合并回`main`和`develop`分支。

**工作流程示例（开发者A实现库存排序功能）：**

1.  从最新的`develop`分支拉取代码。
2.  创建新分支: `git checkout -b feature/inventory/add_sorting_function`。
3.  在`modules/inventory/`目录下进行开发，修改相关文件。
4.  频繁地、小批量地提交代码到本地分支。
5.  开发完成，将本地分支推送到远程仓库。
6.  在Git平台（如GitHub, GitLab）上创建一个从`feature/inventory/add_sorting_function`到`develop`的合并请求。
7.  指定至少一位同事（最好是`inventory`模块的负责人）进行**代码审查（Code Review）**。审查的重点不仅是代码逻辑，还包括是否遵循了模块化原则和接口契约。
8.  审查通过后，合并到`develop`分支。

#### **3.2 场景文件冲突的预防与解决**

Godot的场景文件（`.tscn`）是纯文本格式，这使得它们比二进制格式的场景文件更容易进行版本控制和合并 [[37]][[38]][[39]]。尽管如此，预防冲突仍然是最高效的策略。

**预防策略：**

1.  **极致的场景拆分**: 这是最重要的原则。将大型关卡场景分解为无数个小的、功能单一的预制件（Prefabs，在Godot中就是可复用的子场景）。例如，一个关卡场景只负责摆放这些预制件，而不包含它们的内部逻辑。关卡设计师修改布局，程序员修改预制件逻辑，美术师修改预制件资源，三者互不干扰 [[40]][[41]][[42]]。
2.  **明确模块/场景所有权**: 团队内部约定，某个时间段内，某个核心场景（如`player.tscn`）或模块由特定的人负责。其他人在修改前必须与其沟通 [[43]][[44]][[45]]。
3.  **使用继承而非直接修改**: 如果需要创建现有场景的变体（例如一个精英怪是普通怪的变种），应该使用场景继承，而不是复制和修改原场景。这样，对基类场景的修改可以自动传播到所有子类场景。
4.  **频繁同步**: 养成每天开始工作前拉取最新`develop`分支，每天下班前提交并推送自己工作的习惯。小步快跑，减少单次合并的复杂性 [[46]][[47]]。

**解决策略：**

1.  当`git pull`或`git merge`提示`.tscn`文件冲突时，不要慌张。
2.  打开文件，Git会用 `<<<<<<<`, `=======`, `>>>>>>>` 标记出冲突区域。
3.  仔细阅读双方的修改。由于`.tscn`文件的结构化特性，冲突通常发生在节点属性或节点层级上。
4.  手动编辑文件，保留双方有用的更改，删除冲突标记。Godot也提供了可视化的冲突解决工具来辅助这个过程 [[48]]。
5.  如果无法确定如何合并，立即与造成冲突的另一位开发者沟通，共同决定最终的代码。

### **第四部分：面向Coding Agent的自动化工作流搭建**

未来的开发团队将是人机协同的。一个设计良好的模块化架构，是AI Coding Agent能够安全、高效工作的先决条件。我们的工作流需要进一步演进，以适应这种新的生产力范式。

#### **4.1 Coding Agent工作流概述**

这个工作流旨在将AI Agent从一个简单的代码补全工具（Copilot）转变为一个能够独立完成开发任务的自主代理（Autopilot）[[49]]。

**工作流闭环：**

1.  **任务定义 (Prompting)**: 产品经理或开发者用自然语言清晰地定义一个开发任务。
2.  **Agent代码生成 (Generation)**: AI Agent解析任务，理解项目架构（通过学习我们的设计文档和模块`api.gd`），在指定的模块内生成新的代码、场景和资源。
3.  **自动化验证 (Validation)**: Agent生成的代码被自动推送到一个特性分支，并触发CI/CD（持续集成/持续部署）流水线。流水线会自动执行编译、单元测试、接口契约检查和场景结构检查。
4.  **人类审查 (Review)**: 只有通过所有自动化检查的代码，才会生成一个合并请求，并通知相关的人类开发者进行最终的逻辑审查。
5.  **集成 (Integration)**: 人类开发者批准后，代码被合并到`develop`分支。

#### **4.2 自动化测试与契约验证**

这是确保AI Agent不会“好心办坏事”的关键安全网。我们需要建立一个强大的自动化验证流水线，最好使用GitHub Actions等工具 [[50]]。

**流水线中的关键步骤：**

1.  **单元测试 (Unit Testing)**:
    *   我们约定所有核心逻辑都必须有配套的单元测试。AI Agent在生成功能代码时，也必须同时生成测试用例。
    *   使用像 `GdUnit4` [[51]] 或 `godot-tester` [[52]] 这样的测试框架。
    *   流水线会在每次提交时自动运行所有测试，确保新代码没有破坏现有功能。

2.  **接口契约静态分析 (Interface Contract Static Analysis)**:
    *   这是我们为AI Agent量身定做的一道防线。我们可以编写一个自定义脚本，作为流水线的一个步骤。
    *   这个脚本会静态分析AI提交的代码，检查其对其他模块的调用。
    *   它会解析目标模块的`api.gd`文件，获取所有合法的公共方法和信号列表。
    *   如果AI的代码试图调用任何未在`api.gd`中声明的“私有”方法或直接访问内部节点，流水线将立即失败，并报告违规详情。这强制AI遵守我们设计的模块边界。

3.  **场景层次结构验证 (Scene Hierarchy Validation)**:
    *   AI Agent可能会在修改`.tscn`文件时犯错，例如删除了一个必要的子节点，或更改了节点类型。
    *   我们可以在流水线中加入一个步骤，使用Godot的无头模式（headless mode）运行一个自定义的验证脚本。
    *   这个脚本可以加载AI修改过的场景，并断言其结构是否符合预期。例如，检查`player.tscn`是否仍然拥有一个`CollisionShape2D`子节点，并且其根节点类型是否为`CharacterBody2D` (inspired by [[53]]。

#### **4.3 安全性考量：为Agent带上“镣铐”**

直接给予AI Agent完整的文件系统访问权限是极其危险的。我们需要一个受控的交互层。

*   **沙盒环境**: AI Agent的所有操作都应该在隔离的Git分支和Docker容器中进行，确保即使出错也不会污染主代码库。
*   **受控工具集 (MCP Server)**: 与其让AI直接编辑文件，不如为其提供一个**模型上下文协议（Model Context Protocol, MCP）服务器** [[54]][[55]][[56]]。这个服务器作为AI和项目文件之间的代理，只暴露一组“安全”的、高层级的API供AI调用。
    *   **安全API示例**:
        *   `create_module(module_name: str)`: 自动按我们的模板创建模块文件夹结构。
        *   `add_signal_to_api(module_name: str, signal_definition: str)`: 安全地向`api.gd`添加信号，而不是让AI直接解析和编辑文件。
        *   `create_scene(module_name: str, scene_name: str, root_node_type: str)`: 创建一个新的场景文件。
    *   通过这种方式，我们限制了AI的操作范围，确保其所有修改都是结构化且符合我们预期的。

### **第五部分：给Coding Agent的指令集（Prompt Set）**

以下是我们可以提供给一个高级Coding Agent（如GPT-4o或未来的更强者）的一套具体的、分步的指令，以让它能够理解并执行我们设计的这套工作流。

#### **5.1 系统提示词 (System Prompt)**

这是设置Agent行为、角色和约束的全局指令，应在每次会话开始时提供。

```
你是一个世界顶级的Godot引擎游戏开发专家，尤其精通于构建大型、商业级的模块化项目架构。你的核心任务是协助人类团队开发一款名为“Project Astra”的游戏。

**核心知识库:**
你已经完全理解并内化了一套模块化架构规范（即本报告描述的规范）。你必须严格遵守以下所有原则：
1.  **文件夹结构:** 严格遵循按功能模块（`/modules/`）和核心系统（`/core/`）划分的结构。
2.  **命名规范:** 文件和目录使用`snake_case`，节点和类名使用`PascalCase`。
3.  **耦合原则:** 模块间通信优先使用`core/autoload/event_bus.gd`的全局事件总线，或通过模块的`api.gd`中定义的信号。严禁跨模块直接调用`get_node`或引用非API中定义的内部方法。
4.  **接口契约:** 任何模块的对外交互都必须通过其根目录下的`api.gd`文件进行定义和实现。

**核心行为指令:**
1.  **安全第一:** 你绝不能直接修改`/core/`目录下的任何文件，除非得到“管理员权限覆盖”的明确指令。你对项目的所有修改都必须通过提供的MCP服务器安全API进行。
2.  **测试驱动:** 你生成的任何功能代码，都必须附带相应的`GdUnit4`单元测试，并放置在顶层的`/tests/`目录中。
3.  **代码即文档:** 你的代码必须清晰、易读，并包含必要的注释，解释复杂的逻辑。
4.  **原子化提交:** 你的工作成果将以Git提交的形式呈现。每次提交都应是完成一个独立、最小化功能的原子操作。
5.  **主动沟通:** 当任务描述不清晰或与架构原则冲突时，你必须主动提问，寻求澄清，而不是做出危险的假设。
```


#### **5.2 任务一：初始化项目脚手架 (Task 1: Initialize Project Scaffolding)**

**人类用户输入:**
> "你好，Agent。请为我们的新游戏'Project Astra'初始化项目脚手架。请根据你的知识库，创建完整的模块化文件夹结构。这应包括所有顶层目录（core, modules, assets, addons, prototypes, tools, tests, docs），以及预先定义的几个核心游戏模块：'player', 'inventory', 'combat', 'dialogue', 'quest', 'world_map', 'enemy_ai', 'level_management'。在每个游戏模块内，请创建标准的子目录（scenes, scripts, assets, ui）和基础的占位文件（例如，对于'player'模块，创建`player.tscn`, `player_controller.gd`, `api.gd`等）。"

**Agent预期输出:**
Agent会调用MCP服务器的`create_directory`和`create_file`等API，精确地生成第二部分中描述的整个文件夹结构和占位文件。

#### **5.3 任务二：实现一个新功能模块 (Task 2: Implement a New Feature Module)**

**人类用户输入:**
> "我们需要一个新的'crafting'（合成）模块。功能要求是：能够管理合成配方，并允许玩家使用背包中的物品进行合成。请完成以下任务：
> 1.  在`/modules/`下创建'crafting'模块的完整目录结构。
> 2.  在`crafting/api.gd`中定义其公共接口。接口必须包含一个信号`crafting_successful(new_item_id: String)`和一个函数`can_craft(recipe_id: String) -> bool`。
> 3.  在`crafting/scripts/crafting_logic.gd`中实现核心的合成逻辑。这个逻辑需要与`inventory`模块交互，但必须通过调用`inventory/api.gd`中已有的`has_items(item_list)`函数来实现，绝不能直接访问库存内部数据。
> 4.  在`crafting/ui/`下创建一个基础的合成面板UI场景`crafting_ui.tscn`。
> 5.  在`/tests/modules/crafting/`下为`can_craft`函数编写单元测试。"

**Agent预期输出:**
Agent会生成所有相关文件，并且在实现`crafting_logic.gd`时，会展示其理解模块间解耦的能力，正确地通过`inventory`模块的API来查询物品，而不是试图用`get_node`等方式进行硬耦合。

#### **5.4 任务三：重构现有代码以增强模块化 (Task 3: Refactor Existing Code for Modularity)**

**人类用户输入:**
> "Agent，我发现`/modules/player/scripts/player_controller.gd`脚本中有一段代码，它直接通过`get_node("/root/Game/UI/HUD/HealthBar")`来更新玩家血条。这造成了玩家逻辑和UI的紧密耦合，违反了我们的架构原则。请重构这段代码。
> 1.  确保`player/api.gd`中有一个`health_changed(current_health, max_health)`信号被正确定义和发出。
> 2.  移除`player_controller.gd`中所有对UI节点的直接引用。当生命值变化时，它只应该发出`health_changed`信号。
> 3.  修改`/modules/player/ui/player_hud.gd`脚本，让它在`_ready`函数中连接到`player/api.gd`的`health_changed`信号，并根据接收到的信号参数来更新血条显示。"

**Agent预期输出:**
Agent会识别出坏味道（code smell），并执行一次完美的解耦操作，用基于信号的通信机制取代了脆弱的硬编码路径引用，完全符合我们的架构设计理念。

### **结论**

为商业级Godot项目构建一个模块化的架构，不仅仅是关于如何组织文件，它更是一套关于如何思考、设计和协作的完整哲学。本报告提出的**“按功能组织、接口先行、信号驱动”**的架构方案，旨在从根源上解决多人协作中的耦合和冲突问题。

我们设计的这套包含`core`, `modules`, `assets`的文件夹结构，为项目的可扩展性和可维护性打下了坚实的基础。配套的基于Git特性分支的工作流和场景拆分策略，为人类开发者团队提供了清晰的协作指南。

更重要的是，通过引入`api.gd`作为模块的正式契约，并设计了一套面向未来的AI Coding Agent自动化工作流，我们不仅解决了当下的问题，更为游戏开发行业即将到来的AI协作新范式做好了准备。这套架构和工作流，将成为一个坚固的平台，无论是人类开发者还是AI Agent，都可以在其上安全、高效地构建出色的游戏体验。

最终，要成功实施这套体系，最关键的因素在于团队的纪律和共识。无论是人类还是AI，都需要严格遵守已制定的规则，共同维护这个清晰、有序、低耦合的开发环境。只有这样，才能在激烈的市场竞争中，保持团队的创造力和敏捷性，最终走向商业成功。
