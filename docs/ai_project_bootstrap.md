## 附录：AI 引导的项目快速启动流程

> 当你把 `rules_common.md` 复制到一个新 Godot 项目后，它就成为了这个项目的主规则文件。它本身已经**自包含**所有核心规范（模块化架构、核心行为指令、自动化测试、Git 工作流、命令行环境）。但要让 AI 真正“落地”并驱动项目，还需要补全以下“引用”——它们通常记录在同目录下的 `rules_local.md` 中。
>
> 如果你是 AI，**当检测到 `rules_local.md` 缺失或关键引用缺失时**，按下面的引导流程主动向用户提问并逐项补全。
>
> 如果你是开发者，**在 AI 引导下**按顺序回答，就能快速启动一个新的 Godot 项目。

### A. 必须在 `rules_local.md` 中声明的项目引用清单

| 编号 | 引用项                              | 作用                                                                        | 示例值                                                                |
| ---- | ----------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 1    | 项目名称（Project Name）            | 让 AI 知道它正在服务的“这款游戏叫什么”，回答中会代入项目名                  | `Project Astra`                                                       |
| 2    | 项目类型（Project Type）            | 让 AI 知道这是什么品类的游戏（影响模块规划、行为逻辑）                      | `桌宠 / 2D RPG / 3D 开放世界 / 模拟经营`                              |
| 3    | Godot 根目录名（Godot Root Folder） | `res://` 对应的物理文件夹名；AI 在读写 `.gd` / `.tscn` 时必须知道这一层信息 | `transparent-pet`                                                     |
| 4    | 本地 Godot 调试路径                 | 每次编辑后用 `godot --headless` 验证编译的可执行文件路径                    | `F:\SteamLibrary\steamapps\common\Godot Engine`                       |
| 5    | 测试框架（Test Framework）          | 自动化测试使用的框架                                                        | `GdUnit4`                                                             |
| 6    | 目标平台（Target Platforms）        | CI/CD 构建目标                                                              | `Windows / Web / Android / iOS / Linux / macOS`                       |
| 7    | CI/CD 平台（CI/CD Platform）        | 流水线使用的平台                                                            | `GitHub Actions`                                                      |
| 8    | 项目已存在的模块目录                | 让 AI 知道当前项目已经建了哪些 `modules/xxx`，以便按模块化规范生成代码      | `modules/pet`、`modules/inventory`…（如为空则由 AI 引导设计首个模块） |
| 9    | 向量知识库 / 错误记忆               | 是否启用并管理 `CI-DI.md` 与 `issues.md` 中的错误记忆系统                   | `已启用 / 待创建`                                                     |
| 10   | Git 主开发分支                      | 团队日常在哪个 `dev/xxx` 分支上工作                                         | `dev/fan`                                                             |

### B. AI 引导用户补全引用的对话流程（Prompt 模板）

**当 AI 检测到 `rules_local.md` 缺失或上述引用项缺失时，应按如下结构主动启动对话：**

```text
我注意到本项目的 rules_local.md 还未完整声明项目引用。为了让我按照 rules_common.md 中定义的模块化架构规范为你服务，我需要按顺序确认以下 10 项信息。请依次回答（每项回答一句话即可）：

[1/10] 项目名称（Project Name）：这款游戏叫什么？（例如 "Project Astra"）
[2/10] 项目类型（Project Type）：这是什么品类的游戏？（例如 "桌宠" / "2D RPG" / "3D 开放世界"）
[3/10] Godot 根目录名：`res://` 对应的物理文件夹名是什么？（例如 "transparent-pet"）
[4/10] 本地 Godot 调试路径：你本机安装 Godot 可执行文件的完整路径是什么？
[5/10] 测试框架：你打算使用哪个测试框架？（默认推荐 GdUnit4）
[6/10] 目标平台：你计划构建到哪些平台？（例如 "Windows + Web"）
[7/10] CI/CD 平台：你使用的 CI/CD 平台是什么？（默认推荐 GitHub Actions）
[8/10] 项目已存在的模块目录：当前项目根目录下是否已经有 `modules/xxx`？如果有，列出它们；如果没有，回答"暂无，待设计"。
[9/10] 向量知识库/错误记忆：是否启用 `CI-DI.md` 与 `issues.md`（用于错误记忆 + 向量搜索）？（推荐启用）
[10/10] Git 主开发分支：团队日常在哪个 `dev/xxx` 分支上工作？（例如 "dev/fan"）

我会在收到你的回答后，自动为你生成 `rules_local.md` 文件并提交到当前分支。
```

### C. AI 自动生成 `rules_local.md` 的生成模板

当用户回答完上述 10 项后，AI 按以下模板生成并写入 `rules_local.md`：

```markdown
---
alwaysApply: true
---

## 项目特定规则（本文件只记录"这一个项目"独有的信息）

> 通用规则、模块化架构、Git 工作流、命令行环境规范等跨项目可复用的内容，均记录在同目录下的 `rules_common.md` 中。两份文件均设置 `alwaysApply: true`，共同生效。

**项目身份：**

- 项目名称：<用户回答 1>
- 项目类型：<用户回答 2>
- Godot 根目录名：<用户回答 3>
- 本地 Godot 调试路径：<用户回答 4>

**开发环境：**

- 测试框架：<用户回答 5>
- 目标平台：<用户回答 6>
- CI/CD 平台：<用户回答 7>
- Git 主开发分支：<用户回答 10>

**模块现状（首次启动时由 AI 与用户协同规划）：**

- 已存在模块：<用户回答 8 中列出的 modules/xxx>
- 建议新增模块：<由 AI 基于项目类型自动建议，如桌宠建议：modules/pet（宠物行为）、modules/inventory（道具系统）、modules/interaction（桌面交互）>

**可选增强：**

- 向量知识库 / 错误记忆：<用户回答 9 —— 若启用，AI 将引导设置 `CI-DI.md` 与 `issues.md` 的完整体系>

**本文件维护原则：**

- 只写“这个项目独有的信息”，不重复 rules_common.md 中已有的内容。
- 当项目新增模块、变更目标平台、切换 CI 工具时，**在本文件追加或修改对应条目**。
- 当 rules_common.md 有新版时（例如升级了模块化架构规范），**把新版文件复制过来覆盖即可**，本文件不受影响。
```

### D. 首次启动一个新项目时，AI 的标准工作流

当 `rules_local.md` 已生成且内容完整后，AI 按以下流程启动项目：

1. **确认文件系统状态**：检查 `res://` 根目录下的文件夹结构是否符合 `rules_common.md` 第二部分 2.1 节定义的顶层目录。如果缺失，AI 会主动创建空文件夹（`core/`、`modules/`、`assets/`、`addons/`、`prototypes/`、`tools/`、`tests/`、`docs/`）。
2. **创建第一个模块的 `api.gd`**：根据项目类型，在 `modules/<第一个模块>/api.gd` 中定义该模块对外的公共接口（公共方法、公共信号、公共属性）。此时用户还没有写任何逻辑，但 AI 已经把“契约”立好了。
3. **生成测试用例骨架**：在 `tests/` 目录下，按镜像 `core/` 和 `modules/` 结构的原则，为第一个模块生成基础的 `GdUnit4` 测试文件。测试内容先以“确保场景结构存在”为主，后续迭代增加逻辑测试。
4. **设置 CI/CD 基础**：在项目根目录下生成 `.github/workflows/main.yml` 骨架（基于 `rules_common.md` 第三部分 3.2 节定义的流水线步骤），确保“每次提交 → 无头模式编译 → 运行所有测试”。
5. **首次 `godot --headless` 验证**：运行一次无头模式编译，确保整个骨架能被 Godot 引擎正确加载。
6. **首次原子化提交**：将上述骨架代码推送到 `agent/init-<项目简称>` 分支，合并回 `dev/xxx`，清理 agent 分支。

### E. 常见“缺引用”的快速诊断

当 AI 发现以下任一情况时，应主动向用户提示需要补全 `rules_local.md`：

- 文件中没有“项目名称” → AI 不知道自己在服务哪款游戏。
- 文件中没有“Godot 根目录名” → AI 不知道 `res://` 对应磁盘上的哪个文件夹。
- 文件中没有“本地 Godot 调试路径” → AI 无法执行 `godot --headless` 验证。
- 文件中没有“Git 主开发分支” → AI 无法确定功能分支从哪里切出、往哪里合并。
- 文件中没有“模块现状” → AI 无法判断自己应该在已有模块上改，还是要创建新模块。
